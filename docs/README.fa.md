# ai-handoff

انتقال پروژه از یک هوش مصنوعی به یکی دیگر، بدون اینکه چیزی گم شود.

یک Skill است که خودش کار انتقال را انجام می‌دهد، به‌همراه یک چک‌کننده که نمی‌گذارد پکِ ناقص رد شود.
نه وابستگی دارد، نه کلید API، نه پلاگین. اگر دستور خط فرمان را می‌خواهی پایتون ۳.۹ لازم داری، وگرنه
هیچ چیز. با هر مدلی کار می‌کند که بتواند متن بخواند، از جمله مدل‌هایی که اصلاً اپ ندارند.

برای گرفتن نتیجه، همین امروز هم به اسکریپت نیازی نداری. سه قدم:

۱. از مدل قدیمی پک را بخواه ([پرامپت A](../assets/prompts.md)). حدود ۱۲۰۰ کلمه وضعیت می‌نویسد،

۳. اگر بازگویی غلط بود تصحیحش کن. بعد بگو ادامه بده.

اسکریپت سه چیز اضافه می‌کند: پک را قبل از فرستادن چک می‌کند، نسخه‌ها را مقایسه می‌کند، و به ریپو
یک دروازه‌ی CI می‌دهد. مفید است، ولی اجباری نیست.

## این را قبلاً دیده‌ای؟

سه هفته با یک مدل کار کرده‌ای. پروژه‌ات را می‌شناسد، تُنت را می‌داند، سه راهی که امتحان کردی و
نپسندیدی را یادش است. بعد مدل را عوض می‌کنی یا چت زیادی طولانی می‌شود، و کل تاریخچه را در یک
پنجره‌ی تازه پیست می‌کنی.

مدل جدید می‌خواند و بلافاصله همان چیزی را پیشنهاد می‌دهد که هفته‌ی اول رد کرده بودی.

سه چیز گم شده، و هیچ‌کدامشان جایی نوشته نشده بود:

**چیزهایی که رد کردی، و دلیلش.** این بدترینشان است، چون به شکل یک پیشنهاد مطمئن برمی‌گردد.
«تا حالا LaTeX را امتحان کردی؟» بله. امتحان کردیم. خراب شد.

**سلیقه‌ات.** طول جواب، تُن، زبان، اینکه کد را چطور ببینی. اینها را طی ده‌ها اصلاح به مدل قبلی
یاد داده‌ای و هیچ‌وقت تایپشان نکرده‌ای.

**اینکه کار کجاست.** نه «یک پارسر ساختیم»، بلکه «پارسر CSV را می‌خورد ولی فیلدهای داخل گیومه را نه،
و شمارنده اگر پروسه را وسط کار بکشی دوباره می‌شمارد».

پیست کردن کل مکالمه هیچ‌کدام را منتقل نمی‌کند. فقط مواد خام را می‌برد و از مدل جدید می‌خواهد همان
استنتاج را دوباره انجام دهد، این بار غرق در صد هزار توکن که وسطش بی‌سروصدا فراموش می‌شود. یک برگه
۸۰۰ کلمه‌ای از این آشغال‌دان بهتر جواب می‌دهد، چون اینجا فشرده‌کردن خودِ کار است، نه shortcut.

## بدون اپ هم کار می‌کند؟

بله. و همین دلیل اصلی است که این چیز یک پوشه فایل متنی است، نه یک سرویس وب.

سمت مدل هیچ چیزی نصب نمی‌شود. نه OAuth، نه ثبت در marketplace، نه «حسابت را وصل کن». پک یک فایل
مارک‌داون است و پرامپت boot یک پاراگراف که پیست می‌کنی. اگر مدل بتواند متن بخواند، از عهده‌ی
تحویل‌گرفتن پروژه برمی‌آید.

| مدل چه کاری می‌تواند بکند | تو چه می‌کنی | چه چیزی کار می‌کند |
|---|---|---|
| فایل و git و شل دارد (Claude Code، Cursor، ایجنت محلی) | به ریپو اشاره می‌کنی | همه‌چیز؛ خودش پک را می‌کشد، چک می‌کند، boot می‌زند و نسخه‌ها را مقایسه می‌کند |
| فقط فایل (Claude و ChatGPT و Gemini با پیوست) | پک را پیوست می‌کنی و پرامپت را پیست می‌کنی | همه‌چیز جز اجرای چک‌کننده، که خودت لوکال اجرا می‌کنی |
| بدون فایل، فقط یک کادر متن (بسیاری از مدل‌های محلی) | پک و پرامپت را inline پیست می‌کنی | همه‌چیز. بودجه‌ی ۱۲۰۰ کلمه تا حدی برای همین است که این حالت ارزان بماند |
| هیچ ابزاری ندارد | همان بالا | همان بالا. کل رابط، متن ساده است |

برعکسش هم درست است: مدلی که پک را می‌نویسد هم به فایل دسترسی لازم ندارد. فقط باید مکالمه را
ببیند و پرامپت استخراج را دنبال کند.

تنها محدودیت واقعی این است که مدل با context خیلی کوچک نمی‌تواند هم‌زمان پک و یک کار طولانی را
نگه دارد. آن‌وقت پک را نزدیک ۸۰۰ کلمه نگه دار و اول از همه واژه‌نامه و بخش فایل‌ها را کوتاه کن.

## نصب

**کلون کن.** مسیر معمول همین است:

```bash
git clone https://github.com/borodayeh/ai-handoff.git
cd ai-handoff
python3 -m unittest discover -s tests
```

باید ۳۴ تست پاس شود. اگر نشد، مشکل از پایتون خودت است نه از کد.

```bash
make test        # تست‌ها
make strict      # پک‌های نمونه را چک می‌کند و هشدار را هم خطا می‌شمارد
```

**یا ZIP را دانلود کن** و هر جایی باز کن. مرحله‌ی نصب وجود ندارد و از هر پوشه‌ای اجرا می‌شود.

**یا دستور را نصب کن**، اگر ترجیح می‌دهی به‌جای مسیر، `handoff` تایپ کنی:

```bash
pipx install .          # یا: pip install --user .
handoff validate packs/myproject-pack.md
```

عمداً روی PyPI منتشر نشده: این اسکریپت را باید قبل از اعتماد بشود خواند، و یک پوشه فایل متنی
راحت‌تر از یک wheel قابل بازبینی است.

**یا به‌عنوان skill نصبش کن** تا خود مدل پیدایش کند:

| کجا | چه کار کن |
|---|---|
| Claude Code | پوشه را در `~/.claude/skills/ai-handoff/` کپی کن |
| Claude.ai و رابط‌های وب مشابه | `SKILL.md` و پوشه‌ی `references/` را در یک Project آپلود کن |
| Cursor / Windsurf | محتوای `SKILL.md` را در `.cursor/rules/` بگذار |
| هر چیز دیگر | به مدل دسترسی خواندن این پوشه را بده و بگو از `SKILL.md` شروع کند |

چیزی که باعث پیدا شدن خودکارش می‌شود، frontmatter داخل `SKILL.md` است. روی عوض‌کردن مدل، پر شدن
context، چت جدید، export گرفتن از مکالمه، و کلمه‌های handoff و migrate و checkpoint و resume فعال
می‌شود.

## کِی این کار زیادی است

- چت کوتاه است. دو پیام context را راحت‌تر پیست می‌کنی تا اینکه بخواهی ساختار بدهی.
- کار یک‌بارمصرف است. بعد از تمام شدنش وضعیتی نمی‌ماند که ارزش نگه داشتن داشته باشد.
- قرار است همان‌جا در همان جلسه حلش کنی. اول checkpoint بگیر، بعد انتقال بده.

بقیه‌ی این راهنما فرض می‌کند پروژه‌ای هست که مدتی است در جریان است و بازسازی‌اش از حافظه زمان
واقعی می‌خورد.

## چطور کار می‌کند

سه حرکت. معمولاً فقط اولی و آخری را انجام می‌دهی.

| حرکت | کجا اجرا می‌شود | چه چیزی بیرون می‌آید |
|---|---|---|
| **Extract** | مدل قدیمی | `<slug>-pack.md`، حداکثر ۱۲۰۰ کلمه |
| **Boot** | مدل جدید | بازگویی کوتاه از چیزی که فهمیده، بعد صبر می‌کند تا تو بگویی ادامه بده |
| **Checkpoint** | هر ۲۰ نوبت یا همین حدود | پک به‌روز، با مقایسه نسبت به نسخه‌ی قبل |

پک نُه بخش دارد و هر بخش به این دلیل هست که جلوی یک خرابی مشخص را می‌گیرد:

| § | بخش | جلوی چه چیزی را می‌گیرد |
|---|---|---|
| ۱ | مأموریت | اینکه مدل چیز اشتباهی را بهینه کند |
| ۲ | وضعیت فعلی | ساختن روی چیزهایی که هنوز وجود ندارند |
| ۳ | تصمیم‌ها و گزینه‌های ردشده | تکرار همان بحث قبلی |
| ۴ | محدودیت‌ها | حدس زدن دوباره‌ی سلیقه‌ی تو |
| ۵ | واژه‌نامه | اینکه مدل برای خودش معنی بسازد |
| ۶ | فایل‌ها | نسخه‌های کهنه از فایل‌هایی که از قبل هستند |
| ۷ | پرسش‌های باز | توقف کار روی چیزی که فقط تو می‌توانی تصمیم بگیری |
| ۸ | اقدام بعدی | شروع شدن جلسه با «دوست داری روی چه چیزی کار کنیم؟» |
| ۹ | یادداشت انتقال | حدس بی‌صدا وقتی چیزی کم است |

قواعد کامل هر فیلد و اشتباه‌های رایجی که از آنها پرهیز شده، در
[`references/pack-schema.md`](../references/pack-schema.md) است.

مهم‌ترین قسمت، مرحله‌ی boot است. مدل جدید قبل از اینکه به چیزی دست بزند، در پانزده خط می‌گوید چه
فهمیده و حداکثر سه چیزی را لیست می‌کند که وگرنه باید حدس بزند. هر واقعیتی که گم شده باشد، همان‌جا
به شکل یک خط غلط ظاهر می‌شود، وقتی اصلاحش هنوز ارزان است؛ نه سه ساعت بعد به شکل یک کامیت غلط.

## قدم به قدم

### ۱. استخراج

```bash
python3 scripts/handoff.py new myproject --from-model "claude-sonnet"
```

در ویندوز همان دستور به شکل `py scripts\handoff.py ...` است، یا زیر Git Bash که برای بقیه‌ی این
راهنما ساده‌تر است.

یک `myproject-pack.md` می‌گیری که نُه سرفصل و بودجه‌ی کلماتش از قبل سر جایش است. خودت پرش کن، یا
بگذار مدل قبلی پرش کند:

```
You are being decommissioned. Another model will continue this project with zero access to our
conversation. Write a handoff pack that loses nothing that matters.

Output only the pack. This is a state document, not a transcript: don't summarise our conversation
in order and don't paste conversation content. 1200 words maximum. Tag anything uncertain as
[UNVERIFIED]. Capture what we rejected and why, because that is what transfers always lose. State
my implicit preferences as testable rules ("3 paragraphs max, no preamble", not "be concise").

Schema: 1 Mission (120 words) · 2 Current state (works / half-built / broken / do-not-redo) ·
3 Decisions table (decision | why | rejected alternative | locked?) · 4 Constraints · 5 Glossary ·
6 Artifacts (pointers only) · 7 Open questions (with a named decider) · 8 Next action ·
9 Transfer notes. Last line: "Least confident about: <one thing>."
```

چهار پرامپت، شامل checkpoint و delta، در [`assets/prompts.md`](../assets/prompts.md) است.

### ۲. چک کردن

```bash
python3 scripts/handoff.py validate myproject-pack.md
```

```
554/1200 words · 6 decisions · confidence=medium · [UNVERIFIED]×0 [LOST]×0
VALID
```

اگر رد شود، هنوز پیش‌نویس است. فهرست بررسی‌ها در [پایین‌تر](#چککننده-چه-چیزی-را-رد-می-کند) آمده.

### ۳. کامیت

```bash
git add myproject-pack.md
git commit -m "pack: myproject after week 2"
```

از این به بعد `git log` تاریخچه‌ی checkpointهای توست و `handoff.py diff` می‌گوید بین هر دو نسخه چه
عوض شده.

### ۴. بالا آوردن مدل جدید

```
You are taking over a project from another model. Everything you need is in the pack below.

Step 1. Read the pack. Don't start work.
Step 2. Play back your understanding in 15 lines or fewer, in your own words: MISSION (1 line),
  STATE (2-3 lines), CONSTRAINTS (the 3 most likely to trip you up), NEXT (as your commitment).
Step 3. List up to 3 gaps, contradictions, or things you'd otherwise have to guess. If there are
  none, say "no gaps".
Step 4. Stop and wait for me to say continue.

Don't praise the pack. Treat "locked: yes" decisions as settled. Treat [UNVERIFIED] as hypotheses
to check before building on.

PACK:
<paste myproject-pack.md here>
```

آن بازگویی را درست بخوان. پانزده خط آن‌قدر کوتاه هست که یک واقعیتِ جاافتاده توی چشم بیاید.

### ۵. checkpoint، قبل از اینکه لازم شود

از مدل فعلی بخواه:

```
Produce an updated pack from the current state, same schema. Diff against the previous version:
list changed sections under "CHANGES SINCE LAST PACK", then output only those sections.
```

یا خودت دو نسخه‌ی کامیت‌شده را مقایسه کن:

```bash
python3 scripts/handoff.py diff <(git show HEAD~1:myproject-pack.md) myproject-pack.md -v
```

آن `<(...)` مخصوص bash است. در ویندوز اول نسخه‌ی قبلی را در یک فایل بریز:

```bash
git show HEAD~1:myproject-pack.md > old-pack.md
python scripts\handoff.py diff old-pack.md myproject-pack.md -v
```

یک پک تازه دو دقیقه وقت می‌برد. بازسازی‌اش از یک چت ۳۰۰ پیامی، همان جزئیاتی را می‌خورد که یادت
نمی‌آید.

## دستورها

```bash
python3 scripts/handoff.py new <slug> [--out DIR] [--force]   # ساخت پک خالی
python3 scripts/handoff.py validate <pack.md> [--json]        # چک کردن؛ خروج ۱ در صورت خطا
python3 scripts/handoff.py status <pack.md>                   # تعداد کلمات هر بخش
python3 scripts/handoff.py diff <old.md> <new.md> [-v]        # چه چیزی عوض شده، بخش به بخش
python3 -m unittest discover -s tests                         # اجرای تست‌ها
```

همه با کتابخانه‌ی استاندارد نوشته شده‌اند، خروجی متنی است، و `--json` هست تا CI بتواند استفاده کند.

## گذاشتن روی گیت‌هاب

همین پوشه‌ای که داری، خودِ ریپوست. Skill و schema و چک‌کننده و تست‌ها و CI و مستندات همه داخلش
هستند. هیچ فایلی لازم نیست اول بسازی.

**اگر می‌خواهی پک‌های پروژه‌ات را داخلش نگه داری، خصوصی‌اش کن**، چون پک‌ها وضعیت پروژه را دارند.

### با GitHub CLI

```bash
cd ai-handoff
git init
git add -A
git commit -m "ai-handoff skill v1.0"
gh repo create borodayeh/ai-handoff --private --source=. --push
```

### بدون آن

```bash
cd ai-handoff
git init && git add -A && git commit -m "ai-handoff skill v1.0"
git remote add origin git@github.com:borodayeh/ai-handoff.git
git branch -M main
git push -u origin main
```

### از مرورگر

در `github.com/borodayeh` یک ریپوی جدید بساز، گزینه‌ی **uploading an existing file** را بزن و
محتوای پوشه را بکش و رها کن. ساختار پوشه‌ها حفظ می‌شود. اگر مرورگرت پوشه‌ها را تخت کرد،
`ai-handoff-skill.zip` را لوکال باز کن و پوشه‌ی حاصل را بکش.

### بعد، از هر چت جدید

```
Handoff repo: https://github.com/borodayeh/ai-handoff
Read SKILL.md, then references/boot-protocol.md, then packs/myproject-pack.md. Run boot.
Don't start work until I say continue.
```

مدلی که git دارد از همین‌جا خودش کلون یا pull می‌کند. مدلی که ندارد، پک را inline می‌گیرد.

### پنج دقیقه مرتب‌کاری که ریپو را «تمام‌شده» نشان می‌دهد

گیت‌هاب قبل از اینکه کسی یک خط بخواند، ظاهر ریپو را نشان می‌دهد. تنظیماتی که ارزش دست‌زدن دارند:

| تنظیم | مقدار |
|---|---|
| Description | Move a project between AI models without losing decisions or context |
| Topics | `ai` `llm` `context` `prompt-engineering` `agent-skills` `handoff` `markdown` |
| Website | خالی بگذار، مگر اینکه جایی درباره‌اش بنویسی |
| Features | Issues روشن، Discussions خاموش تا کسی درخواست کند، Wiki خاموش |
| Releases | تگ `v1.0.0` بزن و بخش changelog را در توضیح release بچسبان |

```bash
git tag -a v1.0.0 -m "ai-handoff v1.0.0"
git push origin v1.0.0
```

نشان‌های (badge) بالای ریپو، به‌محض اولین اجرای workflow روی `main`، خودشان کار می‌کنند و نیازی
به ویرایش ندارند.

## با هر مدل چطور

| مدل | چطور اجرا کن | چیزی که خوب است بدانی |
|---|---|---|
| **Claude (وب و دسکتاپ)** | `SKILL.md` و پک را در یک Project آپلود کن | با فایل پیوست بهترین نتیجه را می‌دهد |
| **Claude Code** | در `~/.claude/skills/ai-handoff/` نصب کن، بعد بگو «با ai-handoff checkpoint بگیر» | خودش می‌تواند چک‌کننده را اجرا کند |
| **ChatGPT** | پرامپت A یا B از `assets/prompts.md` را پیست کن و پک را پیوست کن | skill خودکار لود نمی‌شود، پس پرامپت کار را انجام می‌دهد |
| **Gemini** | پک را پیوست کن و پرامپت boot را پیست کن | context بلند دلیل خوبی برای فرستادن کل مکالمه نیست |
| **Cursor / Windsurf** | `SKILL.md` در rules، پک‌ها در `.ai/packs/` | داخل ریپوست، پس فایل‌ها به شکل اشاره می‌مانند |
| **مدل‌های محلی (Ollama، LM Studio)** | پک و پرامپت را inline پیست کن | به سمت ۸۰۰ کلمه کوتاه کن؛ مدل کوچک جزئیات را گم می‌کند |
| **هر مدلی بدون دسترسی به فایل** | inline پیست کن، واژه‌نامه و بخش فایل‌ها را حذف کن | جزئیات در `references/gotchas.md` |

## چک‌کننده چه چیزی را رد می‌کند

| بررسی | نتیجه |
|---|---|
| بخشی نیست، یا هست و خالی است (به‌جایش `none` بنویس) | رد |
| یک placeholder در متن مانده (`{{...}}`، `<PLACEHOLDER>`، `TODO`) | رد |
| یک ردیف تصمیم، گزینه‌ی ردشده ندارد | رد |
| `confidence` یکی از high یا medium یا low نیست | رد |
| «اقدام بعدی» یک قدم مشخص نیست | رد |
| `updated` تاریخ واقعی نیست یا در آینده است | رد |
| کل پک کمتر از ۱۵۰ کلمه است | رد |
| `confidence` برابر high است ولی تگ `[UNVERIFIED]` یا `[LOST]` مانده | هشدار |
| پک بیش از ۱۸۰ روز قدیمی است | هشدار |
| بخشی از بودجه‌اش رد شده، یا پک از ۱۲۰۰ کلمه گذشته | هشدار |
| ردیف تصمیم «چرا» یا `locked?` ندارد | هشدار |
| پرسش باز، تصمیم‌گیرنده‌ی نام‌دار ندارد | هشدار |
| رشته‌ای شبیه کلید API یا کلید خصوصی در متن باشد | هشدار |

CI این را با `--strict` روی همه‌ی `*-pack.md` اجرا می‌کند، یعنی هشدارها هم خطا حساب می‌شوند. یک
پک خراب بی‌سروصدا کامیت نمی‌شود.

## سؤال‌هایی که واقعاً پیش می‌آید

**کل مکالمه را پیست کنم؟**
نه. همین همان خرابی‌ست که این ابزار برای جلوگیری‌اش ساخته شده. وضعیت را بیرون بکش و ۱۲۰۰ کلمه
بفرست.

**اگر چت را از دست داده باشم؟**
به شکل JSON یا HTML اکسپورتش کن، به یک مدل قوی با پرامپت استخراج بده، و صریح ممنوعش کن خلاصه‌ی
زمانی بنویسد. وگرنه دقیقاً همان را تحویلت می‌دهد. بعد سلیقه‌هایت را دستی اضافه کن، چون اکسپورت‌ها
تقریباً هیچ‌وقت اصلاحاتی که کرده‌ای را ندارند.

**برای پروژه‌ی کد هم جواب می‌دهد؟**
بله، با یک قاعده: پک به ریپو اشاره می‌کند و هیچ‌وقت از آن کپی نمی‌کند. در بخش ۶ یک خط اضافه کن که
«قبل از کدنویسی، AGENTS.md یا CLAUDE.md در ریشه‌ی ریپو را بخوان». یادداشت‌های معماری جایشان در
ریپوست، چون نسخه‌ی تکراری داخل پک ظرف چند روز کهنه می‌شود.

**دو پروژه در یک ریپو؟**
اشکالی ندارد. برای هرکدام یک `*-pack.md`. فایل kernel مشترک است و یک بار نسخه‌دار می‌شود.

**چرا اپ وب نیست؟**
چون اول باید فرمت جا بیفتد. الان UI بسازی، یک آخر هفته را صرف انتزاع اشتباه می‌کنی. با markdown
پنج انتقال واقعی انجام بده؛ بخش‌هایی که هر بار دستی ویرایش می‌کنی خودشان می‌گویند اپ چه باید بکند،
اگر اصلاً لازم باشد وجود داشته باشد.

**چه فرقی با «یک خلاصه بده» دارد؟**
خلاصه برای انسانی است که داستان می‌خواند. پک یک سند وضعیت است با گزینه‌های ردشده‌ی اجباری، سطح
اطمینان صریح، و یک دروازه. هیچ‌کس از خلاصه‌ای که چیزی را جا انداخته خجالت نمی‌کشد، و همین باعث
می‌شود خلاصه‌ها همیشه همان چیزها را جا بیندازند.

## وقتی خطا می‌رود

| نشانه | علت احتمالی | راه‌حل |
|---|---|---|
| مدل جدید بلافاصله شروع می‌کند به کد زدن | پرامپت boot اجرا نشده | دوباره بفرست و بگو «اول بازگویی» |
| چیزی را پیشنهاد می‌دهد که قبلاً رد کرده‌ای | بخش ۳ گزینه‌ی ردشده ندارد | اضافه کن؛ از این به بعد چک‌کننده اجبار می‌کند |
| سؤال‌هایی می‌پرسد که چت قبلی جواب داده بود | بخش ۲ یا ۴ نازک است | با delta وصله کن، پک را از نو ننویس |
| به زبان اشتباه جواب می‌دهد | پک به زبان اشتباه نوشته شده | پک را به زبانی بنویس که جواب می‌خواهی |
| چک‌کننده روی `<...>` گیر می‌کند | سینتکس واقعی CLI در متن است | در بک‌تیک بگذارش، code span معاف است |
| به فایل‌ها اشاره می‌کند ولی نقلشان نمی‌کند | دسترسی به فایل ندارد | یک یا دو فایلی که مهم‌اند را inline کن و بگو کردی |
| بعد از شروع کار معلوم می‌شود چیزی گم شده | checkpoint نزده بودی | پک را وصله کن تا اصلاح بماند، بعد ادامه بده |

موارد بیشتر، از جمله تحویل به یک انسان و برگشتن به مدل قبلی، در
[`references/gotchas.md`](../references/gotchas.md) است.

## اگر گیر کردی، یا می‌خواهی با طراحی بحث کنی

- [ROADMAP.md](../ROADMAP.md) چیزهایی را که عمداً ساخته نشده‌اند، با دلیلشان لیست می‌کند. اگر
  می‌خواهی اپ وب یا دکمه‌ی «خلاصه کن» بخواهی، جوابش همان‌جاست.
- [CHANGELOG.md](../CHANGELOG.md) برای اینکه چه چیزی عوض شده.
- [CONTRIBUTING.md](../CONTRIBUTING.md) اگر می‌خواهی تغییری بفرستی. خلاصه‌اش: یک شکست واقعی در
  انتقال بیاور، نه یک نظریه.

  کامیت شود حتی بعد از حذف هم در تاریخچه می‌ماند.
- [Issues](https://github.com/borodayeh/ai-handoff/issues) یک قالب برای «در انتقال چیزی گم شد» دارد،
  که مفیدترین گزارشی است که این پروژه می‌تواند بگیرد.
